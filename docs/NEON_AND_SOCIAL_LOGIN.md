# Neon, Google и GitHub для LEXI

Подключение выполняется поэтапно: сначала проверяем текущую базу, затем Neon, потом GitHub и Google. Ветка подготовки — `codex/lexi-neon-oauth`. Код поддерживает оба способа входа, но кнопки появляются только после настройки ключей соответствующего сервиса. Реальные ресурсы и OAuth-приложения этой инструкцией автоматически не создаются.

Превью формы: [компьютер](previews/oauth-entry-desktop.png) · [телефон](previews/oauth-entry-mobile.png).

## 1. Проверить текущую базу в Render

Откройте [Render Dashboard](https://dashboard.render.com/) → сервис LEXI → **Environment**. Найдите **DATABASE_URL**, не раскрывая и не отправляя его значение в чат.

- Строка есть: определите для себя, указывает ли она на PostgreSQL Render/Neon. Наличие переменной ещё не означает, что Neon уже подключён. Текущую базу не удаляйте.
- Строки нет: текущая версия использует `instance/lexi.sqlite3`. Файл на временном диске Render может не пережить деплой. Если эти аккаунты нужны, сначала сохраните копию базы, до изменения настроек и деплоя. Экспорт прогресса из интерфейса не содержит хеши паролей и не заменяет копию серверной базы.

Существующий **SECRET_KEY** сохраните. Его не нужно менять при подключении Neon.

## 2. Создать базу Neon

1. В [Neon Console](https://console.neon.tech/) создайте проект LEXI. Выберите регион рядом с регионом веб-сервиса Render.
2. В **Connect** выберите базу и пользователя, включите **Pooled connection** и скопируйте полную PostgreSQL connection string. Оставьте параметры `sslmode=require` и `channel_binding=require`, если они присутствуют.
3. Если нужна старая база, сначала выполните перенос из следующего раздела. Если принято решение начинать с чистых аккаунтов, этот перенос можно пропустить.
4. В Render → LEXI → Environment задайте **DATABASE_URL** этой строкой. Добавьте или проверьте остальные настройки:

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | Connection string из Neon, только на сервере |
| `SECRET_KEY` | Существующий постоянный секрет; для нового сервиса — длинное случайное значение |
| `LEXI_PUBLIC_URL` | `https://lexi-m388.onrender.com` |
| `LEXI_COOKIE_SECURE` | `1` |
| `LEXI_TRUST_PROXY` | `1` |
| `LEXI_TIMEZONE` | `Asia/Bishkek` |

5. После переноса и настройки выполните деплой подготовленной ветки. Приложение создаст недостающие таблицы. Сайт хранит пользователей, хеши паролей, фото, прогресс и связи с сервисами в PostgreSQL; деплои веб-сайта эту базу не заменяют.
6. Проверьте регистрацию, выход и повторный вход. В Neon SQL Editor владелец проекта может проверить `SELECT COUNT(*) FROM users;`. Таблицы `users` и `oauth_identities` появятся после первого запуска серверной версии.

Слова пока остаются в JSON-файлах проекта. Это отдельно от постоянной базы аккаунтов. Условия хранения и резервного копирования зависят от выбранного плана Neon.

## Перенос существующих аккаунтов

Инструмент `scripts/copy_accounts.py` читает строки подключения из **LEXI_SOURCE_DATABASE_URL** и **DATABASE_URL**. Не передавайте пароль аргументом командной строки и не добавляйте `.env`/базы в GitHub. `.env.example` содержит только примеры; Python автоматически его не читает.

Исходником может быть сохранённая SQLite или существующая PostgreSQL. Назначение — отдельная пустая база Neon. На время окончательного копирования остановите записи в исходную базу, чтобы новый прогресс не появился уже после снимка. Не переключайте работающий сервис на назначение до окончания копирования.

После установки переменных в окружении выполните:

```sh
.venv/bin/python scripts/copy_accounts.py
```

Это предварительная проверка без копирования: выводится только количество пользователей и связей входа. Для выполнения после проверки:

```sh
.venv/bin/python scripts/copy_accounts.py --apply
```

В Windows используйте `.\.venv\Scripts\python.exe` вместо `.venv/bin/python`.

Копируются идентификаторы, логины, хеши паролей, фотографии, настройки, избранное, история, ревизии и связи с провайдерами. Источник не изменяется. В непустое назначение копирование запрещено; слияния двух баз нет. Маркер прежней очистки прогресса переносится, чтобы она не запустилась заново после перехода. Счётчики временного ограничения попыток не переносятся. Сохраните резервную копию и прежнюю базу до проверки результата.

## 3. Подключить GitHub

1. Откройте [GitHub → Developer settings → OAuth Apps](https://github.com/settings/developers) → **New OAuth App**. Нужен OAuth App.
2. **Application name:** LEXI. **Homepage URL:** `https://lexi-m388.onrender.com`.
3. **Authorization callback URL:**

```text
https://lexi-m388.onrender.com/api/account/oauth/github/callback
```

4. Скопируйте **Client ID**, создайте **Client secret** и добавьте их только в Render Environment:

```text
GITHUB_CLIENT_ID
GITHUB_CLIENT_SECRET
```

5. Выполните деплой/перезапуск с этими настройками. На формах входа и регистрации появится кнопка GitHub. Проверять первый вход следует в обычном браузере. Приложение запрашивает профиль и подтверждённую почту (`read:user user:email`), включая приватную почту; доступ к репозиториям не запрашивается.

## 4. Подключить Google

1. В [Google Cloud Console](https://console.cloud.google.com/auth/overview) выберите или создайте проект. Настройте Google Auth Platform: название LEXI, контактную почту и аудиторию. Для начальной проверки используйте **Testing** и добавьте свою почту в **Test users**.
2. В **Clients** создайте OAuth client типа **Web application**.
3. Добавьте **Authorized redirect URI**:

```text
https://lexi-m388.onrender.com/api/account/oauth/google/callback
```

4. Добавьте выданные значения только в Render Environment:

```text
GOOGLE_CLIENT_ID
GOOGLE_CLIENT_SECRET
```

5. Выполните деплой/перезапуск. Появится кнопка Google. Проверяйте с почтой, добавленной в Test users. Чтобы открыть вход всем, отдельно завершите требования Google к публикации OAuth-приложения. Разрешения LEXI — только `openid email profile`.

Если адрес сайта изменится, обновите **LEXI_PUBLIC_URL** и разрешённые callback URL в обоих сервисах. Для localhost создайте отдельные приложения/ключи с точным адресом локального callback; не отключайте проверку state, nonce или сертификатов.

## Поведение аккаунтов

- Новая подтверждённая почта создаёт новый профиль с пустым прогрессом и первым инструктажем. Логин подбирается автоматически из имени, с учётом уникальности. Пароль Google/GitHub сайт не получает.
- Уже подключённый Google/GitHub открывает тот же профиль по постоянному идентификатору сервиса. Смена отображаемого имени у провайдера не создаёт второй аккаунт.
- Каждый вход или подключение Google запрашивает выбор аккаунта (`prompt=select_account`). После отказа из-за совпадения почты можно снова нажать Google и выбрать другую почту без выхода из Google во всём браузере.
- После подтверждения Google/GitHub успешный callback ведёт на `/auth/complete`. Пока LEXI проверяет установленную серверную сессию, показывается завершение входа; затем автоматически открывается профиль или первый инструктаж без повторного Sign in. При задержке чтение сессии повторяется, а при отсутствии сессии отображается ошибка. Сам адрес завершения не даёт доступ к аккаунту и не кешируется сервис-воркером.
- Совпадение почты с существующим профилем не связывает аккаунты автоматически. Войдите прежним способом — паролем или уже подключённым сервисом — затем откройте **Account → Sign-in methods → Google/GitHub**. Подключение сохраняет прогресс, фото и прежний пароль.
- Один Google и один GitHub можно подключить к одному LEXI. Подключённый идентификатор нельзя перенести в другой аккаунт этим действием. Удаление последнего способа входа и установка пароля для социального профиля в этом этапе не добавлены.
- Используются authorization code, PKCE S256, одноразовый state и Google OIDC nonce/подпись/issuer/audience/expiry. Вход начинается POST-запросом с CSRF; подключение дополнительно проверяет текущий аккаунт. Только подтверждённая почта принимается для создания профиля.
- Access/refresh/ID tokens используются на сервере в ходе текущего запроса; в БД, localStorage и cookie они не записываются. Одноразовый state, nonce и PKCE verifier хранятся в `oauth_states` до 10 минут с привязкой к текущей сессии; после callback удаляются. Запуск и подключение сервиса не перезаписывают login cookie, поэтому запоздавший ответ подключения не восстанавливает прежний вход. Сообщение результата передаётся отдельной короткой подписанной HttpOnly cookie. Сессия LEXI остаётся HttpOnly/SameSite Lax; при HTTPS OAuth автоматически требует Secure cookie.
- Этот этап предназначен для сайта. Возврат OAuth в нативную Android-оболочку через системный браузер/deep link — отдельная задача.

## Проверки и границы

Unit/API-проверки включают реальные локально подписанные OIDC-токены, state/nonce/PKCE, отказ при подмене почты/подписи, связывание аккаунтов и перенос данных с перезапуском. Браузерные проверки перехватывают внешний переход; настоящий вход в Google/GitHub требует собственных ключей. Подключение к рабочей Neon и реальная копия пользовательских данных здесь не выполнялись. Копирование проверено между SQLite; PostgreSQL-настройки/TLS проверены без реального Neon-подключения.
